# Synthea EHR

Learning how electronic health record (EHR) data is structured, and how to ask real-world-evidence (RWE) questions on it — using free synthetic patient data generated by [Synthea](https://github.com/synthetichealth/synthea). Each script is a self-contained "lap" that builds on the SQL foundations from [faers-sql](https://github.com/belalzaky/faers-sql), introducing relational schemas, JOINs, and subquery cohorts.

## What is Synthea?

Synthea is an open-source simulator that generates realistic but entirely fictional patient records — complete EHR histories including diagnoses, medications, encounters, observations, and demographics. Because the patients don't exist, there are no privacy laws (HIPAA), no IRB approval, and no data-use agreements needed. It is the standard dataset for learning healthcare data engineering.

## Relational schema

This project loads five CSV tables into a single SQLite database (`ehr.db`). Every table except `patients` links back to it via a shared UUID:

```
patients  (1 row per person)
│  Id  ◄─────────────────────────────────────────────────────┐
│                                                             │
├──► conditions   (1 row per diagnosis)       PATIENT ────────┤
├──► medications  (1 row per prescription)    PATIENT ────────┤
├──► encounters   (1 row per visit)           PATIENT ────────┤
└──► observations (1 row per measurement)     PATIENT ────────┘

encounters.Id is also a foreign key inside conditions, medications,
and observations (ENCOUNTER column), linking events back to the
specific visit at which they occurred.
```

| Table | Rows | What it stores |
|---|---|---|
| `patients` | 1,171 | Demographics, birth/death date, address, costs |
| `conditions` | 8,376 | Diagnoses with SNOMED-CT codes, start/stop dates |
| `medications` | 42,989 | Prescriptions with drug name, cost, dispenses |
| `encounters` | 53,346 | Visits (ambulatory, wellness, emergency, inpatient) |
| `observations` | 299,697 | Measurements (vitals, labs) with LOINC codes |

## Scripts

| File | SQL concepts | What it does |
|---|---|---|
| `build_db.py` | `CREATE TABLE` via pandas `to_sql` | Loads the five CSVs into `ehr.db` |
| `query.py` | `SELECT COUNT(*)`, `LIMIT` | Verifies row counts; previews the patients table |
| `join_conditions.py` | `JOIN … ON`, table aliases, `WHERE` + `GROUP BY` | Most common conditions among female patients |
| `cohort_meds.py` | Subquery with `IN`, `COUNT(DISTINCT)` | Top medications prescribed to hypertension patients |

## How to run

### 1. Get the data

Download the official Synthea sample CSV dataset:
**[synthea_sample_data_csv_apr2020.zip](https://github.com/synthetichealth/synthea-sample-data/raw/main/downloads/synthea_sample_data_csv_apr2020.zip)**

Unzip it and place the CSV files flat inside a `data/` folder at the repo root:

```
synthea-ehr/
└── data/
    ├── patients.csv
    ├── conditions.csv
    ├── medications.csv
    ├── encounters.csv
    ├── observations.csv
    └── … (other CSVs)
```

`data/` and `ehr.db` are in `.gitignore` — they are generated files, not source code.

### 2. Set up the environment

```bash
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

### 3. Build the database and run the scripts

```bash
python build_db.py          # loads CSVs → ehr.db

python query.py             # row counts + patients preview
python join_conditions.py   # top conditions among female patients
python cohort_meds.py       # top meds for hypertension cohort
```

## What I learned

### Relational schema

Real healthcare databases don't store everything in one flat table. They separate concerns: one table per concept (person, diagnosis, visit, prescription, measurement), linked by shared ID columns. This avoids redundancy and makes queries flexible — you can answer almost any question by joining the right tables. The tradeoff is that you have to understand the schema before you can query it.

### JOINs

`JOIN … ON` stitches two tables together row-by-row wherever a column in one matches a column in the other. `INNER JOIN` (the default) only keeps rows that have a match on both sides. Table aliases (`c`, `p`) are shorthand for table names, essential when two tables share column names like `START` or `PATIENT`.

### Subquery cohorts

A subquery (`WHERE PATIENT IN (SELECT PATIENT FROM conditions WHERE …)`) is the cleanest way to define a patient cohort and then query a different table for those patients. It avoids the double-counting trap that a direct JOIN would introduce when a patient has multiple rows for the same condition — because `IN` is a yes/no check per row, not a row-multiplying operation.

### RWE caveats

**Synthetic data has designed-in associations.** Synthea's simulator assigns medications according to clinical guidelines, so hypertension patients are prescribed antihypertensives and diabetic patients get metformin — by construction, not by observation. Real EHR data is messier: prescribers deviate from guidelines, records are incomplete, and patients take medications for reasons not captured in the data.

**Observational data ≠ causation.** Even on real data, a medication appearing frequently in a condition cohort doesn't mean it causes or treats that condition. Patients with hypertension are also more likely to be older, obese, and diabetic — so their medication lists reflect all of those comorbidities, not just blood pressure treatment. This is **confounding**, and it is the central methodological challenge in every real-world-evidence study.
